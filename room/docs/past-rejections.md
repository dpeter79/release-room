# Past App Review rejections and what fixed them

## App Store review - things that actually got apps rejected

**Dropping a non-sandboxed helper binary is a rejection** (2.4.5 / 2.5.2). Shipping a helper that `removexattr`s its own quarantine and auto-updates on launch is the malware-dropper pattern. Fix: make the app's *own* sandboxed binary do the job via a headless mode (e.g. `--mcp-stdio`) instead of dropping anything.

**`CGEvent.post` to paste into the frontmost app draws 2.4.5 rejections**, twice over for one app, with the reviewer writing *"Accessibility features should not be used for non-accessibility purposes."* The technical position is that the reviewer is wrong: `CGEvent.post` is gated by **`kTCCServicePostEvent`**, a *separate* TCC service from Accessibility, and PostEvent **is** App Sandbox compatible while the real Accessibility APIs are not. System Settings files both under one "Accessibility" heading, which is what invites the mistake. Apple DTS confirms the distinction and then says outright they do not speak for App Review; the forum thread ends **unresolved**. So treat it as a live risk, not a settled one: **spell it out in the review notes** (one ⌘V the user explicitly asked for, never reads the accessibility tree or the screen), and **keep a no-permission fallback** that copies and returns focus so the user presses ⌘V - that way a rejection costs the auto-paste, not the product.

**A spinner with no instructions gets rejected under 2.1(a).** An app was rejected because the "Installing" button loaded indefinitely: macOS was waiting for extension approval in System Settings and the app said nothing. `OSSystemExtensionRequest`'s `requestNeedsUserApproval` callback must drive UI *and* open System Settings - the system notification banner is easy to miss. Sequoia 15+ moved extension approval to General → Login Items & Extensions (`x-apple.systempreferences:com.apple.LoginItems-Settings.extension`), fall back to `...com.apple.preference.security?Privacy` on older macOS.

**A network-only screen that shows a full-page error on ONE failed request gets rejected under 2.1(a).** One app, reviewed just after midnight on an iPad: its main tab showed a *"Check your connection and try again"* error, and that was the whole rejection. Nothing was broken and nothing reproduced afterwards. Ruled out, in order, before accepting that: DNS (A and AAAA both resolve and serve), IPv6-only reachability, the Let's Encrypt cert, the storefront fallback for 3-digit UN M.49 regions, and backend cold start (a fully cold backend and suspended database still answered 200 in 3.2s). The actual cause was structural: the HTTP client had **no retry anywhere**, and that one screen had no local data behind it, so a single transient blip was terminal. A scale-to-zero backend makes it worse in exactly the wrong way, because the first request after a quiet spell is when a blip is likeliest and reviewers work at odd hours, when it is quietest.

Fix pattern, both halves needed: retry idempotent **GETs** twice (1s then 3s) on transport errors and 5xx/429, and cache the last good payload so the screen falls back to content instead of an error. Two traps. **Do not retry `URLError.timedOut`**: that attempt already spent the 30s session budget, and retrying it turned a 30s failure into a **95-second spinner**, measured, which is worse than the error it replaces. And **do not retry POSTs** if an app extension calls one inline; the share extension's `/v1/register` fans out to Apple server-side and a retry loop there sits past the jetsam budget.

**An app that looks like a beta gets rejected under 2.2.** A reviewer on an English iPad saw an English shell over Hungarian-only content and typed "test" into a name field. Not a data bug - a locale mismatch that read as unfinished. Remedy was hard-locking the app to one locale.

**Non-IAP unlock paths get rejected under 3.1.1.** In-app coupon/promo redemption UI had to be removed entirely. Use Apple Offer Codes instead - never an in-app redeem screen. Keeping the dormant server-side coupon tier is fine; the *entry point* is what Apple objects to.

**A screenshot-less / data-less first run is the #1 rejection risk under 2.1.** Fix is a demo-data mode: seeded realistic data run through the *real* engines so every surface is consistent, painted into the UI and the App Group snapshot without persisting to the real store. Gate with a visible "sample data" banner and an exit button.
